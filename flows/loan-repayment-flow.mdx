A repayment is the busiest write path in Apache Fineract. A single `POST /api/v1/loans/{loanId}/transactions?command=repayment` walks through validation, transaction-processor strategy selection, allocation across installments, schedule and summary recomputation, journal entries, lifecycle transitions, and several business events — all inside one `@Transactional` boundary anchored by the command dispatcher. This page traces that path against the current sources.

## The handler

```java
@Service
@RequiredArgsConstructor
@CommandType(entity = "LOAN", action = "REPAYMENT")
public class LoanRepaymentCommandHandler implements NewCommandSourceHandler {
    private final LoanWritePlatformService writePlatformService;
    private final DataIntegrityErrorHandler dataIntegrityErrorHandler;

    @Transactional
    @Override
    public CommandProcessingResult processCommand(final JsonCommand command) {
        try {
            boolean isRecoveryRepayment = false;
            return this.writePlatformService.makeLoanRepayment(LoanTransactionType.REPAYMENT, command.getLoanId(), command,
                    isRecoveryRepayment);
        } catch (final JpaSystemException | DataIntegrityViolationException dve) {
            dataIntegrityErrorHandler.handleDataIntegrityIssues(command, dve.getMostSpecificCause(), dve, "loan.repayment", "Repayment");
            return CommandProcessingResult.empty();
        }
    }
}
```
*(`LoanRepaymentCommandHandler.java:33-51`)*

The first parameter of `makeLoanRepayment` is the transaction type. The same write service method is reused by `MerchantIssuedRefund`, `PayoutRefund`, `GoodwillCredit`, `InterestPaymentWaiver` handlers, each passing a different `LoanTransactionType` enum value.

## Step-by-step

### 1 — Request parsing and command construction

`LoanTransactionsApiResource.executeTransaction` (`LoanTransactionsApiResource.java:550`) inspects `commandParam`. The `repayment` branch (L558) builds the wrapper; every other branch — `merchantIssuedRefund`, `goodwillCredit`, `payoutRefund`, etc. — fans into a different `LoanWritePlatformService` entry point but ultimately reaches the same `LoanAccountDomainServiceJpa.makeRepayment` with a different `LoanTransactionType`. The wrapper is dispatched through the same `PortfolioCommandSourceWritePlatformServiceImpl.logCommandSource` (L611) we covered on the [Command execution flow](/flows/command-execution-flow) page.

### 2 — `makeLoanRepayment` entry

`LoanWritePlatformServiceJpaRepositoryImpl.makeLoanRepayment` (`LoanWritePlatformServiceJpaRepositoryImpl.java:961`) is a thin wrapper that delegates to `makeLoanRepaymentWithChargeRefundChargeType(repaymentTransactionType, loanId, command, isRecoveryRepayment, chargeRefundChargeType=null)` (L1100). The latter parses the body into `transactionDate`, `transactionAmount`, `paymentDetail`, `noteText`, `txnExternalId`, then calls `loanAccountDomainService.makeRepayment(...)` (L1130).

### 3 — Domain service

`LoanAccountDomainServiceJpa.makeRepayment` (`LoanAccountDomainServiceJpa.java:216`) is where the business orchestration sits. It:

1. **Validates client/group state** and that the loan is not closed/overpaid (`validateLoanNotClosedOrOverpaidForTransactions`, L219).
2. **Fires the pre-event** matching the transaction type — for plain repayment, `LoanTransactionMadeBusinessEvent`; for the others, a specific subtype (`getLoanRepaymentTypeBusinessEvent(...)`, L221-222).
3. **Builds the `LoanTransaction`** — `LoanTransaction.repaymentType(...)` (L237) or `LoanTransaction.recoveryRepayment(...)` (L234) carrying the amount, payment detail, date, external id.
4. **Calculates schedule-recalc bounds** — `recalculateFrom` is set when interest recalculation is enabled (L244), and `calculateRecalculateTillDate` (L252) figures out the prepayment horizon.
5. **Holiday / activity validation** — date validations against `HolidayDetailDTO`, last transaction date, client/group transfer date (L256-266).
6. Calls `makeRepayment(loan, newRepaymentTransaction, scheduleGeneratorDTO)` (L270), which delegates to `LoanDownPaymentHandlerServiceImpl.handleRepaymentOrRecoveryOrWaiverTransaction(loan, txn, null, dto)` (the down-payment service handles **all** repayment-like transactions, not just down payments — its name reflects history).

### 4 — Transaction-processor selection

Inside `LoanDownPaymentHandlerServiceImpl.handleRepaymentOrRecoveryOrWaiverTransaction` (`LoanDownPaymentHandlerServiceImpl.java:82`), once amount/date validations pass and the new transaction is added to the loan (L100), the service decides between two paths:

- **Process-latest fast path** — when the transaction is chronologically latest, no adjusted transaction is being replayed, the loan is not in foreclosure, and `canProcessLatestTransactionOnly` returns true, the service calls `loanTransactionProcessingService.processLatestTransaction(strategyCode, txn, ctx)` (L141).
- **Full reprocess path** — otherwise, the schedule is regenerated (`regenerateRepaymentScheduleWithInterestRecalculation` for cumulative, `regenerateRepaymentSchedule` for progressive), and every non-reversed transaction is replayed via `reprocessLoanTransactionsService.reprocessTransactions(loan)` (L167).

`LoanTransactionProcessingServiceImpl.processLatestTransaction` (`LoanTransactionProcessingServiceImpl.java:96`) is a tiny piece of indirection over the strategy factory:

```java
return loanRepaymentScheduleTransactionProcessor.processLatestTransaction(loanTransaction, ctx);
```

where `loanRepaymentScheduleTransactionProcessor` was selected by `transactionProcessorFactory.determineProcessor(transactionProcessingStrategyCode)` (L129). The strategy code comes from `loan.getTransactionProcessingStrategyCode()`. Common values:

- `mifos-standard-strategy` — penalties → fees → interest → principal, applied per installment in order.
- `creocore-strategy` — penalties → fees → principal → interest.
- `early-repayment-strategy` — interest computed against the actual transaction date.
- `advanced-payment-allocation-strategy` — used by progressive loans; allocation order configured per product on `m_payment_allocation_rule`.
- `rbi-india-strategy`, `heavensfamily-strategy`, etc.

Each processor walks the open installments in date order, computing how much of the transaction amount maps to each portion. The mutated `LoanTransaction` ends up with `principalPortion`, `interestPortion`, `feeChargesPortion`, `penaltyChargesPortion` fields populated.

### 5 — Schedule and summary

When the fast path runs but later conditions detect under-allocation, `reprocessOnPostConditions` (L150-159) flips the flow to the full reprocess path. The full path:

- regenerates the schedule via `LoanScheduleService`,
- replays all non-reversed transactions through `ReprocessLoanTransactionsService.reprocessTransactions(loan)` (L167),
- For interest-bearing loans with interest recalculation, replays accruals via `LoanAccrualsProcessingService.reprocessExistingAccruals` / `processIncomePostingAndAccruals` (back in the outer write service, L1138-1139).

### 6 — Lifecycle transition

`loanLifecycleStateMachine.determineAndTransition(loan, transactionDate)` (L173 of the down-payment service) inspects total outstanding and decides whether to flip the loan to `CLOSED_OBLIGATIONS_MET` (no balance, on time), `OVERPAID` (over-allocation), or keep it `ACTIVE`. Multi-disburse over-credit is handled at L179-194.

### 7 — Persistence

Back in the write service after the domain service returns, the new `LoanTransaction` is saved with `loanAccountService.saveLoanTransactionWithDataIntegrityViolationChecks(newRepaymentTransaction)` (mirroring the pattern at L1107 of `LoanWritePlatformServiceJpaRepositoryImpl`), and the loan aggregate is flushed via `saveAndFlushLoanWithDataIntegrityViolationChecks(loan)`. Schedule rows, charges, summary fields, and the loan itself are updated by JPA's dirty-checking.

### 8 — Journal entries

`journalEntryPoster.postJournalEntriesForLoanTransaction(newRepaymentTransaction, false, false)` calls the accounting bridge. For an accrual-based loan product the GL legs are typically:

- **Dr Fund source** (cash, bank, suspense) — the gross transaction amount
- **Cr Loan Portfolio** — `principalPortion`
- **Cr Interest receivable** — `interestPortion`
- **Cr Fee receivable** — `feeChargesPortion`
- **Cr Penalty receivable** — `penaltyChargesPortion`

The exact mappings live on the `LoanProduct` accounting configuration and `acc_product_mapping` table; the bridge is `AccountingProcessorForLoan` (`fineract-provider/.../accounting/journalentry/service/AccountingProcessorForLoan.java`).

### 9 — Delinquency tag and business events

`loanAccountDomainService.setLoanDelinquencyTag(loan, transactionDate)` updates `m_loan_arrears_aging` and the delinquency tag derived columns.

Three post-events typically fire:

- `LoanTransactionMadeBusinessEvent` (or a more specific subtype like `LoanRepaymentBusinessEvent`),
- `LoanBalanceChangedBusinessEvent`,
- `LoanTransactionGreaterThanInstallmentBusinessEvent` when the transaction amount exceeded the due installment.

Each goes through `BusinessEventNotifierServiceImpl.notifyPostBusinessEvent` (`fineract-core/.../BusinessEventNotifierServiceImpl.java:88`), which queues `ExternalEvent` rows tied to the transaction's commit boundary — see [External event emission flow](/flows/external-event-emission-flow).

### 10 — Result and audit

The `CommandProcessingResult` returned by `makeLoanRepaymentWithChargeRefundChargeType` carries `entityId=loanId`, `subEntityId=loanTransactionId`. `SynchronousCommandProcessingService.executeCommand` writes those into `m_portfolio_command_source.resource_id` / `sub_resource_id` (`SynchronousCommandProcessingService.java:186`), then updates `status` to `PROCESSED` with `result_status_code=200` and serialized result body. Finally `publishHookEvent("LOAN", "REPAYMENT", command, result)` (L217) fans the response out to webhook subscribers.

## Failure cases

- **Closed / overpaid loan** — `validateLoanNotClosedOrOverpaidForTransactions` throws an `InvalidLoanStateTransitionException`; the entire transaction rolls back.
- **Holiday violation** — `validateRepaymentDateIsOnHoliday` / `validateRepaymentDateIsOnNonWorkingDay` throws unless the product allows it.
- **Charge constraint** — `loanChargeValidator.validateRepaymentTypeTransactionNotBeforeAChargeRefund` (L1020 of `LoanAccountDomainServiceJpa.makeRepayment`) prevents backdated repayments before an existing charge refund.
- **DB integrity** — `JpaSystemException` and `DataIntegrityViolationException` are caught in `LoanRepaymentCommandHandler` (L48) and translated into `error.msg.loan.repayment.*` codes by `DataIntegrityErrorHandler`.
- **Maker-checker** — `CommandSourceService.processCommand` (L143) throws `RollbackTransactionNotApprovedException` after the handler returns when maker-checker is enabled for `REPAYMENT_LOAN`.
